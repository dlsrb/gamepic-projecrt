# C16 지시 — 규모 확장 실험: 게임 1,500개 + 가상 사용자 1,000명 (실험용 DB 전용) (11/23 채팅)

> `PROJECT.md`, `docs/C14_시뮬_지시.md`, `docs/sim_report.md`와 같이 읽고 시작. 결과는 PROJECT.md 4.11 "결과 (C16)", 지시 외 결정은 따로.
> 목적: "게임·사용자가 많아지면 추천·검색·속도가 어떻게 되나" 확인 (README·발표의 규모 질문 대비). **실제 서비스 확장이 아님.**
> **절대 규칙**
> - 실제 DB(`data/gamepick.db`)·`data/seed.db`·배포 zip·GitHub에는 이 실험 데이터가 **들어가지 않음**. 실험용 사본 `data/big.db`에서만 (`.gitignore` 추가)
> - 실제 서버의 매일 자동 수집 범위(차트·신작)는 **바꾸지 않음**. 이번에 넣는 수집 옵션은 기본값 꺼짐, `--db`로 실험 DB를 줄 때만
> - 스토어 요청은 기존 규칙(1초 간격) 그대로. 스토어 페이지 직접 긁기 없음 (공식 라이브러리·RSS·lookup만)
> - 아이콘 파일은 받지 않음 (실험엔 불필요, 디스크·시간 절약)

## C16-a. 게임 1,500개 모으기 → `data/big.db`
- `data/gamepick.db`를 읽기 전용으로 열어 `data/big.db`로 복사 (지금 280개에서 시작)
- 목표 **약 1,500개** (화면에 보이는 `review_status='ok'` 기준, ±10%면 됨). 모으는 순서·비중:
  1. **상위 게임** (약 70%): 두 스토어의 **장르별 인기 차트**(무료·유료·매출 중 지금 라이브러리·피드로 받을 수 있는 것). 장르마다 상위부터, 장르 간 균형 맞게 (한 장르가 절반 넘지 않게)
  2. **최신 작품** (약 30%): 신작 피드(App Store 신작 RSS, Play 신작 검색 등 기존 C7-f 경로)에서 **최근 출시 순**, 게임 장르만 (C7-f 규칙대로 게임 아닌 앱 거름)
- 같은 게임 판정·검수 대기·별점 0 신작 처리 등은 **기존 `sync_store.py` 규칙 그대로** 재사용 (새로 만들지 말 것). 필요한 옵션만 추가: `--db PATH`, `--target N`, `--genre-charts`
- 새 게임은 기존 규칙대로 자동 태그 + **Play 태그 칩 보강(C12-j `store_tag_map.json`)**까지 적용
- 수집 결과 표: 출처별(차트/신작)·장르별·스토어별(Android만/iOS만/둘 다) 게임 수, 태그 출처별(human/ai/store/auto) 수, 검수 대기·실패 수, 걸린 시간
- 받을 수 있는 차트·피드가 부족해 1,500개에 못 미치면 **억지로 채우지 말고** 모인 만큼으로 진행하고 이유를 적기

## C16-b. 가상 사용자 1,000명 → `big.db`
- C14 시뮬레이터 그대로 사용: `python scripts/simulate_users.py --db data/big.db --users 1000 --seed 42 --days 14` (옵션이 없으면 `--db`만 추가, 기본은 지금처럼 sim.db)
- 유형 비율·행동 규칙은 C14와 **같게** (비교하려고). 바꾸면 결정에 적기

## C16-c. 비교 보고서 `docs/scale_report.md` (맨 위에 "규모 확장 실험(시뮬레이션), 실제 서비스·실제 피드백 아님")
C14(게임 280 · 사용자 300)와 C16(게임 ~1,500 · 사용자 1,000)을 나란히:
1. **속도**: 홈 맞춤 추천·이달의 게임·인기 랭킹·추천 순위·검색·상세의 중앙값/95% (사용자 4명일 때, 시뮬 후). 가장 느려진 API와 원인 추정
2. **비선호 위반**: 홈·이달의 게임 → 0이어야 함
3. **다양성·쏠림**: 추천에 나온 게임 수/전체, 상위 10개 비중, 탐색 칸
4. **태그 출처별 노출·따봉률**, 홈 대체 동작 비율, 미검수 채움 비율 (게임이 늘면 미검수가 늘어나는 영향)
5. **검색**: 결과 0개 검색어, 일부 일치(C15-b) 발생 비율
6. **DB 크기·메모리**: big.db 크기, 서버 한 요청당 게임 목록 로딩 시간 (Catalog가 요청마다 전부 읽는 구조라면 그 비용)
7. **발견한 문제**와 제안 (**고치지 말고** 보고)
- 표·숫자 위주, README·발표에 옮길 수 있게
