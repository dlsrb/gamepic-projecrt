## 7. 발견한 문제와 제안 (고치지 않음)

C16 숫자를 보고 Code가 쓴 분석 (11/24). **고치지 않고 제안만** (실험 DB 기준, 실제 서비스엔 아직 영향 작음 — 1번만 지금 DB에서도 일부 해당).

1. **[가장 중요] 세부 장르를 고르면 장르 필터가 사실상 꺼짐 — 게임이 늘수록 심해짐**
   - 현상: RPG 수집러(설문 3번 `RPG` + `수집형RPG`)의 숨은 취향 일치 100% → **73.7%**. C16에서 이 유형의 홈 "추천" 칸에 전략·시뮬레이션·퍼즐·캐주얼 게임이 나옴 (C14는 전부 RPG). 홈 대체 동작 비율도 28.1% → 4.3%로 크게 줄었는데, 후보가 넓어진 탓이 큼
   - 원인: 설문 답 `subgenre:X` → "X 태그를 가진 게임들의 장르 전부"를 장르 필터에 더함 (`app/reco/survey_map.py` `_tag_genres`). 자동 태그(auto·store)가 붙은 다른 장르 게임에도 세부 장르 태그가 붙어서, `수집형RPG`가 big.db에선 7개 장르 모두에 걸림 → 장르 필터가 7개 장르 = 필터 없음
   - 규모: 세부 장르 22개 중 여러 장르에 걸친 것 — 실제 DB 12개(방치형RPG 5개 장르 등), big.db **21개** (대부분 7개 장르 전부)
   - 비선호 제외는 따로 걸러서 위반은 그대로 0 (이 문제는 "덜 맞는 게임"이지 "싫다고 한 게임"은 아님)
   - 제안: `_tag_genres`가 장르를 셀 때 **검수된 게임(human·ai·manual)만** 보거나, 그 세부 장르 게임의 일정 비율(예: 20%) 이상인 장르만 넣기. 또는 세부 장르는 장르 필터에 안 넣고 점수(선호)로만. 어떤 자동 규칙이 다른 장르 게임에 `수집형RPG`·`MMORPG`를 붙이는지(키워드·Play 칩) 같이 확인
2. **속도: 게임 5.4배 → 모든 API가 약 3배 (중앙값 44 → 128~155ms, 95%는 최대 169ms)**
   - 6개 API가 거의 같은 비율로 느려짐 → 요청마다 게임 수에 비례하는 공통 비용. 사용자·반응이 3.5배로 늘어난 영향은 작음 (C16 시뮬 전 → 후 +4~11ms)
   - `/api/popular` 한 요청 프로파일 (1,500개, cProfile): `Catalog` 만들기 약 27ms (게임·태그 전부 `load_games` 20ms + games 테이블 전체), `profile_for`의 `set_best_score`(취향 % 기준으로 모든 게임 점수) 약 13ms, 카드 만들기·JSON 약 10ms. 홈 맞춤 추천은 여기에 모든 후보 점수·거르기가 더해짐
   - 가장 느린 API는 검색(155ms, 원래도 가장 무거움: 전체 게임 이름·태그 비교 + 일부 일치 계산), 가장 많이 느려진 API는 홈 맞춤 추천·이달의 게임(×3.0)
   - 제안: 게임 목록(Catalog)을 프로세스 메모리에 두고 수집·검수 때만 새로 읽기, `set_best_score`를 사용자별로 저장. 사용자 테스트 규모(게임 300개 안팎)에선 필요 없음 — **게임이 수천 개가 되면** 할 일
3. **미검수 게임 비중이 커짐: 홈 노출의 41.5% → 54.4%** (store 13.2% → 39.7%)
   - 게임이 늘면 검수된 게임(79개)은 그대로라 자동 태그 게임 몫이 늘어남. 따봉률은 출처별로 비슷(store 9.0%, human 7.7%)한데, 시뮬의 숨은 취향이 같은 태그로 재는 구조라 **태그가 틀려도 시뮬에선 안 드러남** (실제 정확도는 사람이 봐야 함)
   - 제안: AI 초안 다음 묶음을 "홈 노출이 많은 미검수 게임"부터 (`data/big_metrics.json`의 노출 순위 참고)
4. **검수 대기가 많음: 새 게임 1,220개 + 검수 대기 298개 (추가 시도의 약 20%)**
   - 장르 차트에는 시리즈·비슷한 이름 게임이 많아 "비슷한 이름 → 사람이 판단" 규칙(C7)이 자주 걸림. 실제 서비스가 이 규모로 늘면 사람 검수 부담이 큼
   - 제안: 개발사·번들 ID가 같으면 자동 판정 범위 넓히기 검토 (지금 규칙은 안전한 쪽이라 그대로 두는 것도 방법)
5. **신작 경로로는 새 게임이 0개** (목표 30%를 못 채움 → 차트가 대신 채움, 결정 1)
   - App Store 신작 피드 3개(328개 항목) 중 DB에 없는 게임은 4개뿐 — 실제 서버의 매일 수집이 이미 가져감. 후보(App Store 4 + Play 신작 검색 111개) 중 90일 넘음 93 · 출시 예정 3, 나머지도 추가되지 않음 (그 전에 게임 아닌 앱 181건은 후보에서 거름, C7-f 규칙 그대로)
   - 실제 서비스엔 문제 아님 (매일 수집이 신작을 이미 잘 가져오고 있다는 뜻). 실험 결과의 출처는 차트 100%
6. **스토어 치우침: 새 게임 중 Android만 486 · iOS만 133 · 둘 다 601** — Play 장르 차트는 200개, App Store 장르 RSS는 100개까지만 와서. Play 유료 차트 2개(레이싱·단어)는 응답이 비어 실패로 기록 (나머지 차트는 정상)
7. **다양성은 오히려 좋아짐**: 상위 10개 비중 17.9% → 12.9%, 홈에 나온 게임 933개(전체의 62%), 탐색 칸 서로 다른 게임 147 → 313
8. **검색**: 결과 0개 검색어 0개 (C15-b 일부 일치가 받침, 일부 일치 3.5%), 이름 검색 99.8% — 실패 1건 `자동` → "자동차 충돌 시뮬레이터"는 두 글자 검색어에 맞는 게임이 많아 화면 개수 밖으로 밀린 것으로 추정
9. 그 밖에 이상 없음: 비선호 위반 0 (홈 48,156 · 이달의 게임 26,496 노출), 같은 게임 따봉 중복 0, 수집 실패 0, DB 10.3MB · Catalog 한 번 4MB
