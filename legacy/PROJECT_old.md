## 3. 트랙 A: 리뷰 데이터 분석

### 3.1 스토리라인
제목(가제): **「별점이 말하지 않는 것 — 문장 단위 감정 분석으로 본 모바일 게임 리뷰의 실제 반응」**

핵심 주장: 별점은 리뷰를 숫자 하나로 압축해 정보를 잃는다. 문장 단위로 나누면 별점이 숨기는 불만이 보인다.
(예: "스토리 좋아요. 근데 과금 유도가 심해요. 그래도 5점" → 긍정 2, 부정 1)

| 연구 질문 | 가설 |
|---|---|
| RQ1 별점과 문장 감정은 얼마나 어긋나는가 | H1 4~5점 리뷰에도 부정 문장이 의미 있는 비율로 있다 |
| RQ2 고별점 리뷰 속 부정 문장의 주제는 | H2 과금·광고에 집중된다 |
| RQ3 대형 vs 인디 불만 주제 차이 | H3 대형은 과금·운영, 인디는 버그·최적화 |
| RQ4 평가와 무관한 문장 비율 | H4 '관계없음' 비율이 무시할 수 없는 수준 |
| RQ5 Android vs iOS 불만 차이 | H5 Android에서 발열·최적화 불만 비중이 더 높다 |

### 3.2 데이터 수집
- **게임 약 100개**, 8~10개 장르. 설치 수 기준 대형 30 / 중견 40 / 인디 30
- **Google Play (주 데이터)**: 대형 게임당 최대 1,000(수집은 1,500), 중견 400(수집 600), 인디 전량. `google-play-scraper`, ko/kr, 최신순, 최근 12개월
- **App Store (보조 데이터)**: 공개 고객 리뷰 RSS 피드, 게임당 최근 일부(약 500건, 실제 수집 후 확인). 제목+본문 합침
- **기준 수량**: 전처리 후 **25,000건 이상** (Google Play만으로 충족)
- 개인정보(닉네임, 프로필) 저장 안 함

**출력 형식 (Gemini 크롤러와 합의된 규격)**
- 입력: `data/game_list.csv` — `game_id, name, tier, genre, android_id, ios_id`
- 출력: `data/raw/android/{game_id}.csv`, `data/raw/ios/{game_id}.csv`
- 컬럼: `platform, game_id, review_id, content, score, date(YYYY-MM-DD), app_version, thumbs_up, has_reply`
- 로그: `logs/failed.txt`, `logs/summary.csv`

### 3.3 전처리
중복 제거 → 결측 제거 → 짧은 리뷰(공백 제외 10자 미만) 제거 → 정규화(반복 문자 축약, URL·쿠폰코드 마스킹, **탭·줄바꿈 → 공백**) → `kss`로 문장 분리

### 3.4 라벨링
- 단위: **문장 1개 = 라벨 1개**
- 라벨: **0=부정, 1=긍정, 2=중립, 3=관계없음** (기존 이진 분류 의미 유지)
- 경계 규칙: 혼합 문장은 대비 접속(~는데, ~지만) 뒤 기준 / 반어는 실제 의미 / 불만 담긴 건의=부정, 단순 건의=중립 / 게임 관련 질문=중립, 무관한 문의=관계없음
- 과정: 파일럿 200문장(직접) → 층화 추출 약 3,000문장(게임별·별점별 균등, App Store 15~20%, 중립·관계없음 보충) → Gem 1차 → 전수 검수 → Gem–최종 일치율 기록 → (선택) Cohen's kappa
- 주제(과금·광고·버그·발열·운영)는 라벨이 아니라 **분석 단계의 키워드 사전 후처리**

### 3.5 모델 (수업 코드 `KOELECTRA-Finetune.py`)
- 입력: 탭 구분 `id, document, label` (NSMC 형식)
- 4분류를 위해 `num_labels=2 → 4` 변경 필요 (**교수님 허용 여부 확인 필요**)
- 코드는 정확도만 계산, 토크나이저 미저장, 8:2 비층화 분할(`random_state=2026`) → 평가·추론은 별도 스크립트로
- 플랫폼·게임·별점 메타데이터는 학습 파일과 분리해 `data/review_sentences_meta.csv`에 `id` 기준 저장

### 3.6 README 보고서
`README.md` 작성 완료(템플릿). 1장(문제 정의·가설), 4장(라벨링 정의) 완성. 나머지는 ✍️ 자리에 실제 수치·그림 채워야 함.

## 4. 트랙 B: 게임픽 웹 + 추천 시스템

### 4.1 추천 시스템 설계 (확정 방향)
**콘텐츠 기반 + 2단계 + 개인 피드백.** 다른 사용자가 없어도 작동(콜드 스타트 해결), 리뷰 없는 인디·신작도 추천 가능.

1. **후보 거르기**: 사용자가 직접 고른 대분류 장르만 남김, 비선호 태그 가진 게임 제외 → "RPG 골랐는데 FPS 나오는" 문제 차단
2. **순위 매기기**: 태그 종류별 무게를 다르게 한 가중 코사인 유사도
   - 무게: 장르 3.0 / 세부장르 3.0 / 시점·그래픽 2.0 / 플레이 1.0 / 분위기 1.0 / 과금 0.5
3. **설문 → 태그 가중치** (트리 분기 없음). "좋아하는 게임 고르기"로 그 게임의 태그를 취향에 반영
4. **반응으로 태그 점수 갱신 (11/2 변경)**: 해당 게임이 가진 태그의 점수를 올리고 내림
   - 👍 따봉 **+1.0** / 스토어 이동 **+0.5** / 관심 없음 **−1.0**
   - 태그 점수는 **0점에서 시작**, 범위 **−5 ~ +5** (넘으면 잘라냄)
   - 설문 시작 점수(제안, 확인 필요): 선호 태그 **+2** / 좋아하는 게임의 태그 **+1**(겹치면 합산) / 비선호 태그 **−5**(후보에서 제외)
   - 남용 방지: 따봉은 게임당 1회(취소 시 −1 되돌림), 스토어 이동 점수는 게임당 하루 1회만 반영
5. **탐색 슬롯 20%**: 같은 장르 안의 인디·신작 노출
6. **(예정) 리뷰 분석 감점**: 사용자가 싫어하는 주제(예: 광고)의 부정 비율이 높은 게임 감점. 모델 완성 전에는 키워드 기반 임시 표로 대체

향후(기획서에만): 사용자가 충분히 모이면 협업 필터링을 섞는 혼합형(3단계).

**LLM의 역할은 보조**: 태그 자동 추출(사람 검수), 자연어 검색 → 태그 변환, 추천 이유 문장 생성. 추천 결정은 하지 않음. 구조는 수업 MCP 코드(m06)처럼 "DB 도구 결과만 근거로 답함". → "그냥 AI 챗 쓰면 되지 않냐"에 대한 답: 게임픽의 AI는 게임픽 DB(검증 태그, 리뷰 분석, 내 반응 기록)로만 답한다.

### 4.2 추천 엔진 프로토타입 (`gamepick_reco/`, 완성)

### 4.4 페이지 구조 (11/2 확정)

**① 첫 시작 화면 = 취향 설문** (처음 방문 때만. 다시 오면 바로 홈)
- 보이는 것: 질문 하나씩 슬라이드, 모두 객관식
- 행동: 선택, 다음, 이전, 건너뛰기(필수 질문 이후 등장), 슬라이드 모션
- 이동: 다음/이전 질문, 끝나면 홈

**② 홈**
- 보이는 것: 설문 맞춤 게임 카드(처음엔 카드만), 추천 카드(신작·인기), 검색창, 랭킹(추천 순위 1~10위), 오른쪽 위 동그라미 프로필, 설정, 최근 본 게임(오른쪽 작은 네모), 다크모드 토글
- 행동: 게임 카드 / 검색창 / 랭킹 / 프로필 / 설정 / 최근 본 게임 선택, 다크모드 전환, **관심 없음**
- 이동: 카드·랭킹·최근 본 게임 → 상세 / 검색창 → 검색 / 프로필 → 마이페이지 / 설정 → 설정

**③ 검색**
- 보이는 것: 검색 결과 게임 카드(부합도 표시), 키워드 박스, 추천 검색어, 자동완성
- 행동: 검색, 키워드 선택, 게임 카드 선택, 추천·자동완성 검색어 선택
- 동작: 키워드는 위쪽 박스로 표시, 카드는 그 아래 / 검색어를 선택하면 검색창에 입력만 되고 바로 검색되지 않음

**④ 게임 상세**
- 보이는 것: 썸네일, 이름, 설명, 영상, 별점, 순위, 부합도, 👍 따봉, **스토어 이동**, 뒤로가기, 홈, 비슷한 게임 카드, **맨 아래: 리뷰 분석(핵심 가치 ②)**
- 행동/이동: 영상 재생 / 별점 → 점수별 개수 시각화 / 순위 → 이 게임과 다른 게임 순위 / 따봉 → 추천 수 증가 + 취향 반영 / 비슷한 게임 → 그 게임 상세 / 뒤로가기 → 직전 페이지 / 홈 → 홈
- 리뷰 분석 영역: 별점별 긍정·부정 문장 비율, 주제별 불만(과금·광고·버그·발열·운영). 모델 완성 전엔 "임시 분석" 표시

**⑤ 마이페이지**
- 보이는 것: 닉네임, 프로필 이미지, 취향 분석 시각화
- 행동: 닉네임 변경(한글 2~10자, 영어 4~12자, 혼합 최대 12자, 서버에서도 검사)

**⑥ 설정**
| 항목 | 내용 |
|---|---|
| 화면 | 라이트 / 다크 / 시스템 따라가기 |
| 취향 | 설문 다시 하기, 비선호 태그 관리, 추천 기록 초기화 |
| 개인정보 | 내 데이터 내려받기, 내 데이터 삭제 |
| 정보 | 개인정보 처리방침, 이용약관, 오픈소스 라이선스, 버전 |

### 4.5 보안 방침
- 개인정보 최소 수집: 임시 ID와 닉네임만. 이메일·전화번호·실명 받지 않음
- API 키는 서버 `.env`에만. 프론트·GitHub에 노출 금지(`.gitignore`, `.env.example`만 공개)
- 입력 검증: 파라미터 쿼리(SQL 인젝션), 출력 이스케이프(XSS), 길이·형식 서버 검사
- 요청 횟수 제한(검색·반응 남용), 보안 헤더(CSP 등), 배포 시 HTTPS
- 로그인 추가 시: 비밀번호 해시(bcrypt/argon2), HttpOnly·SameSite 쿠키

### 4.9 DB 설계 (초안)
| 테이블 | 주요 컬럼 | 용도 |
|---|---|---|
| `users` | `id`(임시 UUID), `nickname`, `survey_done`, `exp_group`(random/survey/feedback), `created_at` | 임시 사용자, 실험 그룹 |
| `games` | `id`, `name`, `developer`, `tier`(대형/중견/인디), `description`, `thumbnail_url`, `video_url`, `android_url`, `ios_url`, `release_date`, `store_rating`, `store_rating_count` | 게임 정보 |
| `tags` | `id`, `name`, `category`(genre/subgenre/view_graphic/play/mood/paywall) | 태그 사전 (무게는 category로 결정) |
| `game_tags` | `game_id`, `tag_id` | 게임–태그 연결 |
| `survey_answers` | `user_id`, `question_id`, `answer` | 설문 응답 원본 (재계산·분석용) |
| `user_tag_scores` | `user_id`, `tag_id`, `score`(−5~5) | 취향 점수 |
| `reactions` | `id`, `user_id`, `game_id`, `type`(like/store/dislike/view), `created_at` | 반응 기록, 최근 본 게임, 추천 수, 랭킹 |
| `review_stats` | `game_id`, `star`(1~5), `pos`, `neg`, `neu`, `irr`, `source`(temp/model) | 별점 분포 + 별점별 문장 감정 (상세 맨 아래) |
| `review_topics` | `game_id`, `topic`(과금/광고/버그/발열/운영), `neg_count`, `neg_ratio`, `source` | 주제별 불만, 리뷰 감점 |
| `search_logs` | `keyword`, `created_at` (사용자 ID 저장 안 함) | 추천 검색어 |

- 다크모드 등 화면 설정은 DB가 아니라 브라우저에 저장
- 추천 수 = `reactions`의 like 개수, 따봉 취소 시 해당 행 삭제
